# システム仕様

拡張機能、MCPサーバー、フォーム画面が外から見てどう振る舞うかを定めます。各項目はシステムテスト(`test/system`)で検証します。拡張機能の項目は、配布物をVS Codeの代役の上で動かして検証します。

## フォームの設計図

### SPEC-FORM-001 設計図の形

AIはフォームを次の形のJSONで指定する。

| キー          | 型             | 必須 | 制約        |
| ------------- | -------------- | ---- | ----------- |
| `title`       | 文字列         | ○    | 1〜80文字   |
| `description` | 文字列         |      | 300文字以下 |
| `fields`      | 項目の配列     | ○    | 1〜20個     |
| `computed`    | 計算結果の配列 |      | 8個以下     |

項目は`type`で種類を区別し、すべての項目が次を持つ。

| キー            | 型         | 必須 | 制約                                                                 |
| --------------- | ---------- | ---- | -------------------------------------------------------------------- |
| `id`            | 文字列     | ○    | 英字か`_`で始まり、英数字と`_`だけの40文字以下                       |
| `label`         | 文字列     | ○    | 1〜60文字                                                            |
| `description`   | 文字列     |      | 質問が何を聞いているか。120文字以下                                  |
| `reason`        | 文字列     |      | 推奨の理由。選択肢以外の項目では値を決める助けになる助言。60文字以下 |
| `reasonDetails` | 文字列     |      | 推奨の詳しい理由。300文字以下                                        |
| `default`       | 種類による |      | 推奨する値                                                           |
| `advanced`      | 真偽値     |      | 真なら「詳細」の中に畳む                                             |

AIは根拠を持って勧められるときだけ`default`を付ける。`reason`と`reasonDetails`は`default`のある項目にだけ付けられる。推奨のない質問の説明は`description`に書く。

種類ごとのキーは次のとおり。

| `type`   | キー                                                                                                                             |
| -------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `text`   | `default`(500文字以下)、`placeholder`(80文字以下)、`multiline`                                                                   |
| `number` | `default`、必須の`min`と`max`、`step`(正の数)、`prefix`と`suffix`(各8文字以下)                                                   |
| `choice` | 必須の`options`(2〜6個。各`value`と`label`は1〜60文字、`description`は60文字以下、`details`は300文字以下)、`default`、`multiple` |

最上位の選択項目の選択肢は、任意の`fields`(1〜10個の項目の配列)を持てる。`fields`の項目は、その選択肢が選ばれている間だけ有効になる。`fields`の中の選択項目の選択肢は`fields`を持てない(入れ子は1段まで)。

計算結果は`id`、`label`、`expression`(300文字以下)と、任意の`prefix`、`suffix`、`decimals`(0〜4)、`primary`を持つ。

表示する文章の文字数は目安である。次のキーは、表の文字数の2倍まで受け付け、2倍を超えたら誤りとして返す。

- 設計図の`title`と`description`
- 項目の`label`、`description`、`reason`、`reasonDetails`、`placeholder`
- 選択肢の`label`、`description`、`details`
- 計算結果の`label`

AIは文字数を正確に数えられず、英語は同じ内容に日本語より多くの文字を使う。目安を少し超えただけの設計図を誤りとして返すと、AIが作り直す間、利用者が待たされる。

AIに示すJSON Schemaには、これらのキーの`maxLength`として受け付ける上限を書き、目安は`description`に「Aim for 60 characters or fewer.」の形で書く。VS CodeのCopilotは、ツールを呼ぶ前にAIの入力をこのJSON Schemaで検査する。`maxLength`に目安を書くと、目安を1文字超えた設計図はAsk Formに届く前に拒否される。

`id`、選択肢の`value`、`default`、`expression`、`prefix`と`suffix`の文字数は目安ではなく上限であり、超えたら誤りとして返す。

- 項目と計算結果の`id`には、計算式の真偽値の予約語`true`と`false`を使えない。大文字と小文字は区別する。
- `__proto__`は有効な`id`として扱い、計算結果の表示と回答の`computed`にもその名前で保持する。

派生元: REQ-ASK-001, REQ-ASK-002, REQ-ASK-003

### SPEC-FORM-002 設計図の意味的な検査

次のいずれかに当たる設計図は受け付けず、問題をすべて列挙して返す。

- 項目と計算結果の`id`が重複している
- 数値項目で`min`が`max`以上、または`default`が範囲外
- 選択項目の選択肢の`value`が重複している
- 選択項目の`default`が選択肢にない、または`multiple`と`default`の形(単一か配列か)が合わない
- `default`のない項目に`reason`か`reasonDetails`がある
- 複数選択の`default`に同じ値が複数ある。空の配列や重複のない配列は受け付け、選んだ数と計算で使う数を一致させる
- 計算式が文法に合わない、または未定義の`id`や自分より後の計算結果を参照している
- 複数選択の選択肢が`fields`を持っている
- `fields`の中の選択項目の選択肢が、さらに`fields`を持っている
- 選択肢の`fields`も含めた項目の合計が40個を超える

項目の`id`の重複は、選択肢の`fields`の項目も含めて調べる。

派生元: REQ-ASK-001, REQ-ASK-004

### SPEC-EXPR-001 計算式

計算式は次を使える。評価できない場合(0での割り算など)の結果は「—」と表示する。

- 数値、`"`か`'`で囲んだ文字列、`true`、`false`
- 項目と、自分より前の計算結果の`id`。選択肢の`fields`の項目も参照でき、その選択肢が選ばれていないときは未定義になる。数値項目は数値、単一選択は選んだ`value`、複数選択は選んだ数、文字列項目は文字列になる
- `+` `-` `*` `/` `%`、比較`<` `<=` `>` `>=` `==` `!=`、論理`&&` `||` `!`、条件`条件 ? 値 : 値`、かっこ
- 関数`min` `max` `abs` `floor` `ceil` `round`(`round(値, 桁数)`も可)

- `1e999`など有限でない数値リテラルは評価できないものとし、回答の計算結果は`null`になる。その値を使う比較や後続の計算結果も評価できない。短絡評価や条件分岐で使われない値は結果に影響しない。

派生元: REQ-ASK-003

## MCPサーバー

### SPEC-MCP-001 質問のツール

MCPサーバーは、AIから呼べるツール`ask_form`を公開する。

- 入力は SPEC-FORM-001 の設計図
- 読み取り専用で外の世界に触れない注釈(`readOnlyHint: true`、`openWorldHint: false`)を持ち、実行前の確認も結果の確認も求めない
- `_meta.ui.resourceUri`で SPEC-MCP-002 の画面を指す

派生元: REQ-ASK-001, REQ-ANS-001

### SPEC-MCP-002 画面のリソース

MCPサーバーは`ui://ask-form/form.html`を、MIMEタイプ`text/html;profile=mcp-app`の1つのHTMLとして返す。

派生元: REQ-ASK-001

### SPEC-MCP-003 回答を待つ

`ask_form`は、画面から結果が届くまで結果を返さない。結果は次のいずれかで、`structuredContent`と、同じ内容のJSONを含む文章で返す。

| `status`         | 意味                             | ほかのキー                                                                                 |
| ---------------- | -------------------------------- | ------------------------------------------------------------------------------------------ |
| `submitted`      | 送信した                         | `values`、`held`、`delegated`、`changedByUser`、`computed`、`comments`、`heldForm`、`note` |
| `answer_in_chat` | キャンセルした。チャットで答える | なし                                                                                       |
| `unavailable`    | 利用者が不在の設定で、質問しない | なし                                                                                       |

- `values`には、最上位の項目と、選ばれている選択肢の`fields`の項目のうち、値のある項目だけを入れる。選ばれていない選択肢の`fields`の項目は入れない。
- 空欄のまま送信した文字列の項目は、空文字列を値として`values`に入れる。
- `held`には、あとで決めるにした項目の`id`を、`delegated`には、おまかせにした項目の`id`を、設計図の順に入れる。どちらの項目も`values`に入れない。あとで決めるかおまかせにした選択項目の選択肢の`fields`の項目は、`values`にも`held`にも`delegated`にも入れない。
- `heldForm`には、`held`の項目の設計図を、題名と`fields`の形で入れる。AIはこれを元に`ask_form`で聞き直せる。`held`が空なら`heldForm`のキーを入れない。
- `changedByUser`には、`values`に入る項目のうち、推奨と違う値にした項目と、推奨がなく利用者が答えた項目の`id`を入れる。
- あとで決めるかおまかせにした項目を参照する計算結果は`null`になる。
- `comments`には、利用者が質問に書いたコメントを、項目の`id`から文章への対応で入れる。前後の空白を除き、空のコメントは入れない。コメントがなければ`comments`のキーを入れない。
- `note`には、利用者が書いた補足を、前後の空白を除いて入れる。補足が空なら`note`のキーを入れない。

`structuredContent`には、AIが次にすべきことを書いた文章を`next`として加える。`submitted`の`next`には、空文字列は利用者が意図して空欄にした答えであること、`held`の項目の値を決めつけず、その値に依存しない作業を進め、必要になったら`heldForm`を元に聞き直すこと、`delegated`の項目は聞き直さずに自分で決め、何を選んだかを利用者に伝えることを指示する。`comments`があるときは、各コメントをその項目に当てはめるよう指示する。`note`があるときは、食い違う値より補足に従い、補足が`held`の項目に答えていればそれを使うよう指示する。`answer_in_chat`の`next`には、作業を区切って利用者の発言を待つよう指示する。

利用者が不在の設定(SPEC-EXT-007)のとき、`ask_form`は設計図を検査した後、待たずに`unavailable`を返し、待機の表示も出さない。`unavailable`の`next`には、聞き直さず、推奨した値で進め、推奨のない質問は自分で判断し、置いた前提を利用者に伝えるよう指示する。設計図に誤りがあれば、不在の設定でも SPEC-MCP-004 の誤りを返す。

待っている間に利用者が不在になったときも、`ask_form`は待つのをやめて`unavailable`を返す。その待機は取り消しと同じく消え、以後その鍵への`form_answer`は SPEC-MCP-005 の誤りになる。

- 複数選択の差分は並び順を無視し、値ごとに比べる。値にNUL文字があっても、異なる選択は`changedByUser`に含める。

派生元: REQ-ANS-001, REQ-ANS-003, REQ-ANS-005, REQ-ANS-006, REQ-ASK-004, REQ-WAIT-002

### SPEC-MCP-004 設計図の誤り

`ask_form`は SPEC-FORM-001 または SPEC-FORM-002 に反する設計図を受け取ると、待たずに誤りとして返し、AIが直せるよう問題の一覧を示す。

派生元: REQ-ASK-001

### SPEC-MCP-005 回答を受け取るツール

MCPサーバーは画面専用のツール`form_answer`を公開する。AIからは見えない(`_meta.ui.visibility`が`["app"]`)。

- 入力は、フォームの鍵、操作(`submit`、`chat`)、`values`、`held`、`delegated`、`comments`、`note`
- 鍵に対応する待機中の`ask_form`に結果を渡す。同じ鍵の待機が複数あれば先に始まったものから順に渡す
- `values`を設計図に照らして検査し、合わなければ誤りを返す
- 有効な項目は、`values`に値があるか、`held`か`delegated`の一方に`id`があるかのどれか1つでなければ誤りを返す。値のある項目や有効でない項目を`held`か`delegated`に入れた場合と、同じ`id`を両方に入れた場合も誤りを返す
- `comments`が項目の`id`から文字列への対応でないか、有効でない項目へのコメントか、500文字を超えるコメントがあれば誤りを返す
- 複数選択の回答に同じ値が複数あれば拒否し、画面の選択数と計算結果が食い違う値を受け付けない
- `note`が文字列でないか、2000文字を超えていれば誤りを返す
- 鍵に対応する待機がなければ、受け付けられないことを示す誤りを返す
- 回答を渡す処理が待機数の通知中に中断されても、台帳から外した質問には回答が届き、未完了の待機を残さない

派生元: REQ-ANS-001, REQ-ANS-005, REQ-ANS-006, REQ-ANS-007, REQ-CANCEL-001

### SPEC-MCP-006 フォームの鍵

フォームの鍵は、`ask_form`が受け取った引数をそのまま正規化したJSONから決まる。キーの順序が違うだけの引数からは同じ鍵が得られ、画面とサーバーで同じ鍵になる。

派生元: REQ-ANS-001

### SPEC-MCP-007 中断

`ask_form`の呼び出しが取り消されると、その待機は消え、以後その鍵への`form_answer`は SPEC-MCP-005 の誤りになる。

HTTPの応答を切断しなくても、同じMCPセッションから届く`notifications/cancelled`の`requestId`に対応する呼び出しを取り消す。他の呼び出しは待機を続ける。

画面専用の読み取り専用ツール`form_status`は、フォームの鍵を受け取り、`pending`(待機中)、`answered`(回答済み)、`cancelled`(中断)、`unknown`(記録なし)を返す。確認するだけでは回答や待機数を変えない。

派生元: REQ-CANCEL-001

### SPEC-MCP-008 送り直しのツール

MCPサーバーは画面専用のツール`form_resend`を公開する。設計図と、ツールの結果としてCopilotへ渡した回答と、新しい回答を受け取る。回答は、値(`before`、`after`)、おまかせにした項目の`id`(`beforeDelegated`、`afterDelegated`)、コメント(`beforeComments`、`afterComments`)で渡す。値のない有効な項目のうち、おまかせにないものは、あとで決めるとして扱う。差分がなければ誤りを返す。差分があれば、差分を述べた文章と、新しい回答の値、`held`、`delegated`、`comments`を書いたJSONの添付を返す。値、あとで決める、おまかせの間の変更と、コメントだけの変更も差分に数える。添付はMCPのリソース`ask-form://answers/<uuid>/<slug>.json`として読め、送り直しごとに別のリソースになる。表示名は題名から整形した`<slug>.json`とし、UUIDを含めない。

- 自動送信のツールは公開せず、文章と添付を準備するだけとする。
- 添付は拡張機能の永続領域へ保存してから返す。同じ保存先を使う新しいサーバーでも同じURIから読み取れ、64件を超えて新しい添付を作っても消えない。保存失敗はツールの誤りとして返す。
- リソースの読込はUUIDとファイル名で保存先を参照する。存在しない添付と保存先の外を指すパスは拒否する。
- 添付名は40コードポイントまでとし、補助平面の文字を分断せずURIに符号化できる。

派生元: REQ-RES-002, REQ-RES-003

### SPEC-MCP-009 接続の保護

MCPサーバーは`127.0.0.1`の空いているポートでだけ待ち受け、起動ごとに作る秘密のトークンを`Authorization`ヘッダーに持たない要求と、`Origin`ヘッダーを持つ要求を拒否する。

派生元: REQ-SEC-001

## フォームの画面

### SPEC-UI-001 初期表示

画面は質問ごとに、質問名、質問の説明、入力欄か選択肢を表示する。`default`があれば、その値で始める。`advanced`の項目は閉じた「詳細」の中に表示する。

- 選択肢には`description`と`details`を表示する。`default`の選択肢には「推奨」の印を付け、その選択肢の中に推奨の理由(`reason`と`reasonDetails`)を表示する。
- 文字と数値の項目に`default`があれば、推奨する値を表示し、`reason`と`reasonDetails`があれば理由も表示する。利用者が値を変えたら「推奨に戻す」を表示し、押すと推奨の値に戻して入力欄にフォーカスを戻す。
- `default`のない単一選択と数値の項目は、未回答で始める。先頭の選択肢や`min`を初期値にしない。見出しに「未回答」と示す。未回答の項目が残る間は送信できず、送信しようとしたら、その項目を無効と示し、最初の未回答の項目にフォーカスを移す。未回答の項目は、答えるか、あとで決めるかおまかせ(SPEC-UI-012)にすると送信できる。
- `default`のない文字列の項目は空欄で、複数選択の項目は何も選ばれていない状態で始める。どちらもそのまま送信でき、空欄や選択なしという答えになる。
- 質問は詳しい説明(`details`と推奨の理由)を畳める。最初は開いている。選択肢をポインターで選ぶと、その質問を畳む。見出しを押すか、キーボードで質問の中に入ると開く。畳む対象がない質問には開閉のしるしを出さない。
- 開閉、続きの質問の出入り、選んだ行の色の変化には短い動きを付ける。動きを減らす設定のときは付けない。
- 複数選択の値にNUL文字があっても異なる選択への変更を検出する。並び順だけの違いは変更と扱わない。

派生元: REQ-ASK-002

### SPEC-UI-002 計算結果

画面は値が変わるたびに計算結果を更新する。`primary`の計算結果は大きく表示する。

派生元: REQ-ASK-003

### SPEC-UI-003 回答の操作

画面の操作は「キャンセル」と「送信」の2つのボタンだけとする。「送信」は画面の値を`submit`で送り、「キャンセル」は値を送らずに`chat`で閉じる。フォーム内で⌘/Ctrl+Enterを押すと「送信」と同じ操作になる。そのとき入力中の値は先に確定し、数値は範囲内に収める。

派生元: REQ-ANS-001, REQ-ANS-003, REQ-ANS-004

### SPEC-UI-004 回答後の要約

送信後、画面は要約に切り替わる。要約には、最上位の項目と、選ばれている選択肢の`fields`の項目を並べ、値か「あとで決める」か「おまかせ」を示す。推奨から変えた項目には、元の推奨を添える。コメントのある項目には、値の下にコメントを示す。補足を送信していれば、項目の後に補足を示す。ツールの結果を受け取ったときも同じ要約を表示する。`answer_in_chat`の後は「回答せずに閉じました」と示し、値を示さない。`unavailable`の結果を受け取ったときは「質問に自動で応じる設定(chat.autoReply)が有効なため、質問せずに進めました」と示し、値も回答の操作も示さない。先に中断を示していても、この表示に改める。この表示の後に遅れて届いた`form_answer`の返答では、表示を変えない。

派生元: REQ-RES-001, REQ-ANS-006, REQ-ANS-007, REQ-WAIT-002

### SPEC-UI-005 送り直し

要約の「変更して送り直す」で編集に戻る。ツールの結果としてCopilotへ渡した回答から値を変えた項目の見出しに「前回: 〜」と前回の値を示し、値かコメントを変えた項目の数を示す。値もコメントも回答と同じなら送信ボタンを押せない。ボタンを押すとSPEC-MCP-008を呼ぶ。

- デスクトップ版では、返った文章と`resource_link`添付をMCP Appsの`ui/message`でフォームのある会話の入力欄に置くだけとし、自動送信しない。要約に戻り「チャットの入力欄に入れました。内容を確かめて送信してください」と示す。英語では同じ内容を英語で示す。利用者がその会話の入力欄でEnterを押して送信する。
- 入力欄に置けなければ、「このフォームのある会話を開き、入力欄を空にしてから、もう一度送ってください」と示し、編集を続けられる。
- パネルのフォームは送信すると閉じるので(SPEC-EXT-004)、要約と送り直しはチャットの中のフォームにだけある。
- 下書きを置いても差分の基準は更新しない。下書きを送信しなかった場合も同じ変更を再び置ける。基準の回答に戻した場合だけ変更なしとする。
- 下書きの準備中は編集できない。要約は最後に下書きへ置いた編集値を示す。再編集のキャンセルではその値に戻し、差分の基準と混同しない。

- 複数選択の値にNUL文字があっても異なる選択なら送り直せる。並び順だけの違いでは送り直せない。

派生元: REQ-RES-002, REQ-RES-003

### SPEC-UI-006 中断と期限切れ

ツールの取り消しを受け取ったとき、または`form_answer`が受け付けられないと返したとき、画面はそれを示し、回答の操作をできなくする。

回答を待つ画面は`form_status`でも状態を確認し、ホストが`ui/notifications/tool-cancelled`を送らなくても、サーバーが中断を記録していれば中断を表示する。未登録や通信の誤りは中断と扱わない。回答後や中断後は確認を止め、遅れた返答で要約を閉じたり中断したフォームを再開したりしない。

- 初期化の直後に中断の通知を受け取っても、中断を表示する。状態の定期確認や回答の試行を待たない。

派生元: REQ-CANCEL-001

### SPEC-UI-007 テーマ

画面は、MCP Appsのホストから受け取る色と文字の変数を使い、変数がなければVS Codeの変数を使う。ハイコントラストのテーマでは、ボタンと切り替えに枠線を付ける。

派生元: REQ-LOOK-001

### SPEC-UI-008 アクセシビリティ

画面の操作要素はすべてラベルを持つ本物のフォーム部品で作り、フォーカスが見え、axeの検査で違反がない。

派生元: REQ-A11Y-001, REQ-ANS-004

### SPEC-UI-009 表示の言語

画面の文言は、ホストから受け取るロケールが日本語なら日本語、それ以外なら英語で表示する。

派生元: REQ-LOOK-001

### SPEC-UI-011 選択肢ごとの項目

画面は、選択肢の`fields`の項目を、その選択肢のすぐ下に、左の縦線と字下げを付けて表示し、選ばれている選択肢の項目だけを見せる。

- 選択を切り替えて別の選択肢の項目で値を直しても、フォームを閉じるまでその値を覚えておく。回答、要約、送り直しには、選ばれている選択肢の項目だけを使う。
- 送り直しでは、回答になかった項目が現れたら、回答からの変更に数える。
- 選択肢の`fields`の項目の`advanced`は無視する。
- 親の選択項目をあとで決めるかおまかせにすると、どの選択肢の`fields`の項目も見せない。

派生元: REQ-ASK-004

### SPEC-UI-012 あとで決める、おまかせ

画面は、どの質問にも、答えずに送る手段として「あとで決める」と「おまかせ」を持たせる。

- 見出しの右端に、答え方のメニューを出す。選択肢は「答える」「あとで決める」「おまかせ」で、最初は「答える」とする。フォームの縦の長さを増やさないため、選択肢や入力欄の行には足さない。「答える」の間は目立たせず、あとで決めるかおまかせの間はメニューを強調する。
- あとで決めるかおまかせにすると、選択項目は選択を外し、数値と文字列の項目は入力欄を空にする。「答える」に戻すと、その前の値に戻る。
- 文字列の項目も同じメニューを持つ。空欄の文字列の項目は、あとで決めるとは扱わず、空欄という答えとして送る。
- 値を入れるか選択肢を選ぶと、メニューは「答える」に戻る。
- 計算結果のうち、あとで決めるかおまかせにした質問を参照するものは「—」と表示する。
- 未回答の質問を示すときは、メニューではなく、選択肢か入力欄にフォーカスを移す。
- 送信すると、あとで決めるにした質問を`held`、おまかせにした質問を`delegated`として渡す(SPEC-MCP-005)。送り直しでは、どちらもそのまま編集に戻し、値を変えたら「前回: あとで決める」のように示す。

派生元: REQ-ANS-005

### SPEC-UI-013 補足

回答の画面は、質問と計算結果の後、ボタンの前に、閉じた「補足を書く」を持つ。

- 開くと、複数行の入力欄と、「選択肢にない答えや、Copilotに伝えたいことを書けます。回答と一緒に届きます。」の案内を表示する。フォームの縦の長さを増やさないため、最初は閉じておく。
- 入力欄は2000文字までしか受け付けない。送信してから長すぎると分かる事がないようにする。ブラウザによる文字の数え方の違いに左右されないよう、入力のたびに画面でも長さを確かめて切り詰める。
- 送信すると、入力欄の文章を`note`として渡す(SPEC-MCP-005)。入力欄で⌘/Ctrl+Enterを押しても送信できる。
- 補足を書いても、未回答の質問が残る間は送信できない。答えが選択肢にない質問は、あとで決めるにして、その質問のコメント(SPEC-UI-014)か補足に答えを書く。
- 送り直しの編集には補足を出さない。送り直しはチャットの入力欄に下書きを置くので、伝えたいことはそこに書ける。下書きを置いた後の要約にも補足を出さない。下書きには補足が入らないので、補足も送り直したように見せない。

派生元: REQ-ANS-006

### SPEC-UI-014 項目ごとのコメント

画面は、どの質問にも、その質問へのコメントを書く手段を持たせる。

- 見出しの右端、答え方のメニューの左に「コメント」のボタンを出す。読み上げでは「件数へのコメント」のように質問名を含めて読む。フォームの縦の長さを増やさないため、コメントを書くまでは入力欄を出さない。
- ボタンを押すと、その質問の下に2行の入力欄を出し、フォーカスを移す。コメントを書いた質問では、ボタンの代わりに入力欄を出し続ける。
- 入力欄は500文字までしか受け付けない。
- 入力欄の案内は、答える質問では「この質問について、Copilotに伝えたいことを書けます。」とする。あとで決めるにした質問では、何が分かれば決められるかを、おまかせにした質問では、決めるときに重視してほしいことを書くよう促す。
- 送信すると、コメントを`comments`として渡す(SPEC-MCP-005)。送り直しでも編集でき、コメントだけを変えても送り直せる。

派生元: REQ-ANS-007

### SPEC-UI-010 画面への通知の送り主

- 初期化、ツールの結果、中断、ホストの表示設定、呼び出しへの返答は接続先のホストからだけ受け付ける。別のウィンドウやフレームから届いたメッセージで画面や回答の受け付け状態を変えない。
- ホストのoriginが分かる場合は一致も検査する。直接読めない場合は、そのホストから最初に受け付けたJSON-RPCのoriginを保持し、以後異なるoriginを拒否する。

派生元: REQ-SEC-001, REQ-CANCEL-001

## 拡張機能

### SPEC-EXT-001 MCPサーバーの登録

デスクトップ版の拡張機能は、起動時に SPEC-MCP-009 のMCPサーバーを動かし、VS CodeにHTTPのMCPサーバーとして登録する。

- 待ち受けの開始に失敗した場合は起動の失敗として呼び出し元に返し、MCPサーバーを登録しない。非同期の失敗も未処理の例外にしない。

派生元: REQ-ASK-001, REQ-SEC-001

### SPEC-EXT-002 待機の表示

待機中の`ask_form`が1つ以上ある間、ステータスバーに「Copilotが回答を待っています」を表示する。

- フォームがチャットの中にあるときは、表示を押すとチャットを開く。
- フォームをパネルに表示しているとき(SPEC-EXT-004)は、表示を押すと、回答を待つフォームのパネルを前面に出す。複数あれば、先に待ち始めたフォームを出す。チャットにはフォームがないので、チャットを開いても利用者はフォームにたどり着けない。

派生元: REQ-WAIT-001

### SPEC-EXT-004 web版

拡張機能は、`ask_form`と同じ入力と結果を持つツールを拡張機能のツールとして登録し、呼ばれるとフォームをエディター横のパネルに表示して回答を待つ。web版ではこのツールを常に有効にする。

- チャットの停止でツールの呼び出しが取り消されたら、パネルを閉じる。読み込み中でも閉じる。回答できないパネルを残さない。チャットは開かない。
- 閉じたパネルには何も送らない。
- 送信せずにパネルを閉じたら、「キャンセル」と同じ`answer_in_chat`を結果として返し、回答待ちの表示を消す。
- 「送信」を押したら、結果を返してパネルを閉じる。質問のたびに回答済みのパネルがタブとして残り、利用者が自分で閉じることになるのを避ける。フォーカスは、VS Codeがパネルを閉じたときに戻す場所に任せる。
- 「キャンセル」を押したら、パネルを閉じてチャットを開き、入力欄にフォーカスを移す。利用者はチャットで答えると決めたので、役目を終えたパネルを残さない。チャットを開けない環境でも、結果を返してパネルを閉じる。
- パネルのホストは`form_resend`を持たない。パネルには要約が残らず、送り直しの入口がない。

- web版の受け入れテストは、拡張機能側の正常終了とブラウザ側の回答・パネルが閉じたことの確認が両方成功してから終了する。片方でも失敗すれば失敗とする。

派生元: REQ-WEB-001, REQ-CANCEL-001

### SPEC-EXT-006 MCPを使わない環境

設定`askForm.mcp.enabled`(既定は有効)を切ったとき、または`chat.mcp.access`が`all`でない(組織がMCPを制限した)とき、デスクトップ版の拡張機能はMCPサーバーを提供せず、設定の変更をVS Codeに通知する。このとき拡張機能のツール(SPEC-EXT-004)を有効にし、デスクトップ版でもフォームをパネルに表示する。それ以外のデスクトップ版では、二重に見えないようにこのツールを無効にする。

- 拡張機能のツールはデスクトップ版でも登録し、有効かどうかはマニフェストの`when`で決める。

派生元: REQ-ENV-001

### SPEC-EXT-007 利用者が不在の設定

拡張機能は、VS Codeの設定`chat.autoReply`が有効な間、利用者が不在であるとMCPサーバーに伝える。VS Codeの組み込みの質問ツールは、この設定が有効なら質問せずに進める。フォームも同じ設定に従う。

- 設定は`ask_form`が呼ばれるたびに読む。VS Codeを再起動しなくても、設定の変更が次の質問から効く。
- 拡張機能のツール(SPEC-EXT-004)も、この設定が有効な間はパネルを開かず、待機の表示も出さずに、`unavailable`の結果を返す。
- フォームが回答を待っている間に設定が有効になったら、待っているフォームにも`unavailable`を返す。パネルのフォームは閉じる。VS Codeの組み込みの質問ツールも、待っている質問を同じように省く。
- VS Code 1.144は、待たずに結果を返した`ask_form`のフォームをチャットに表示しない。SPEC-UI-004の`unavailable`の表示は、結果とともに画面を表示するホストのためにある。

派生元: REQ-WAIT-002

### SPEC-EXT-005 起動・サイズ・検査の予算

拡張機能はVS Codeの起動完了後に読み込まれる。バンドルの読み込みと起動処理は`budgets.json`の`activationMs`以内に終わり、各バンドルの大きさは`budgets.json`の`size`の上限を超えない。

- `timed.ts`による検査は`budgets.json`の時間を超えたら終了を要求し、1秒の猶予後に強制終了して失敗とする。受け入れテストを含む子と孫を同じプロセスグループで止め、直下の子だけが先に終了しても強制終了を取り消さない。Windowsではプロセスツリーを終了する。

派生元: REQ-PERF-001

## リリース

### SPEC-REL-001 配布前の検査と公開

- mainへのpushでpackage.jsonかCHANGELOG.mdが変わったとき、またはworkflow_dispatchで開始する。originに`v<version>`がなければ実行コミットにタグとリリースを作り、既存なら公開をスキップする。タグの照会失敗時は公開しない。同時に複数のリリースを実行せず、実行中のリリースを取り消さない。

- タグはpackage.jsonのversionに`v`を付けたものと一致し、版数は先頭の余分な0や接尾辞のない`major.minor.patch`とする。CHANGELOG.mdの`## <version>`の項には空でない箇条書きが1つ以上必要で、不備があれば公開を止める。
- minorが奇数ならプレリリース、偶数なら正式リリースとする。検査CLIは判定をGITHUB_OUTPUTがあれば追記し、なければ標準出力に出す。任意の第2引数で指定したファイルに対象版の本文だけを書き出す。
- リリースは検査とテスト後にVSIXを作り、その版の変更履歴を説明としてGitHub ReleasesへSHA256SUMS.txtとともに公開し、VSIXの出所を証明する。トークンがある配布先だけ追加公開し、各配布先へプレリリースの指定を渡す。
- CIのVSIX成果物は単一ファイルをZIPに包まず保存し、test-resultsはZIPを維持する。

派生元: REQ-DIST-001
